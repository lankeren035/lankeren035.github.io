项目实现 · 统一目录总图

总图采用一棵 backend 目录树。同一文件夹只出现一次，模块编号表示教程归属；目录内部用左右区域区分模块。图 1 模板文件保持原样，总图使用该模板当前的文件、类与函数内容。

目录合并

目录 模块归属 内容
indexing/ 模块 2 左；模块 1 右 解析、HTML、编码、Writer；Milvus 与父块 Store
rag/ 模块 4 左；模块 3 右 LangGraph 证据工作流；召回、合并、精排与改写
chat/ 模块 7 左；模块 6 右 对话编排；Runtime、请求 ctx、会话存储
tools/ 模块 5 知识与天气 Tool
schemas/ 模块 6 Chat、Trace、HITL 协议
infra/、db/、env.py 模块 1 连接与缓存、ORM 模型、环境加载

箭头含义

  • 实线：函数调用或 LangGraph 的节点调度。
  • 虚线：数据 / 对象传递，包括 ctx、模型、证据、状态和批量记录。
  • 远距离使用编号引用，避免穿越多个模块。4.F33 表示模块 4 里的 F33；内部冒号表示目标步骤。
  • 工厂返回闭包 Tool，传入 ctx 不表示立即执行检索。Writer 调用编码和写入服务，EmbeddingService 不直接调用 MilvusStore。
  • 图 1 文件本身的图形、文本与连线不修改；总图只重新安排文件位置，合并目录，并重建少量近处连线。

主流程

  1. 问答调用：Service 执行 Agent → 知识 Tool → RAG 图 → 检索入口 → 知识存储；证据逐级返回后由 Agent 回答，Service 保存。
  2. ctx 传递：Service 创建 → Runtime 接收 → 知识 Tool 闭包绑定 → RAG 节点共享；步骤事件经 Queue 返回流式 Service。
  3. 入库数据：DocumentLoader 输出三级 Chunk；教程调用方先筛选 L1/L2 写 PG / Redis，再筛选 L3，经 Writer 编码、组装后写 Milvus。
  4. HITL：metadata 保存任务与快照 → 下一轮用户补充 → 专用入口重建状态并检索评分 → Service 依据新证据直接回答或继续追问。
