图_7Agent对话编排模块

对应 [[7_代码实现_Agent 对话编排]]。把历史、工具调用、证据、HITL、长期记忆和 SSE 汇成一次完整对话。

正常问答

加载会话与 metadata → 建立本轮 ctx → 保存用户消息 → “长期笔记 + 最近 6 条历史 + 当前问题” → 创建并运行 Agent → Tool / RAG → 读取结构化 Trace → 标准化追问或保留回答 → 更新 metadata → 保存 AI 消息和 Trace → 关闭 ctx。

跨轮 HITL

只有存在有效 resume_state 时，主入口才绕过外层 Agent，调用 _resume_rag_from_hitl_sync() → pipeline.resume_rag_from_hitl()。返回后，有证据就通过主模型生成回答，仍缺信息就重建 pending_hitl。合法 pending_hitl 却无快照时，使用拼接补充的兼容路径重新进入 Agent；不能把“存在 pending_hitl”都画成直接恢复。

流式与持久化

正常分支由内部 _agent_worker() 生产文本事件，ctx 把 RAG 步骤写进同一个 Queue，外层异步生成器按 SSE 格式输出。Trace 和 hitl_request 在主文本之后发送。[DONE] 发出后还要更新笔记和保存消息，直到生成器结束才完成收尾；图中按源码保留这一顺序。

函数框不是一份新实现；路径和函数名均映射本版本源码。内嵌 _agent_worker() 保持函数橙色，不画成类。工具选择和答案生成交给 Runtime 装配的 Agent；Service 负责业务状态与输出协议。

图形约定

绿色是目录，蓝色是文件，紫色是类，橙色是函数；标题中的名称与职责之间保留 12 个空格。类框中的编号通常对应其方法；函数框的编号描述内部步骤。没有组合，矩形宽高可分别调整。

图_6Agent状态管理模块

对应 [[6_代码实现_Agent 状态管理]]。区分数据协议、单次请求状态、跨轮会话存储和 Agent 运行装配。

四块分别解决什么

  1. schemas/chat.py 定义合法的数据形状：真实证据、主 / 子 Trace、HITL 恢复和 Chat 会话结果。字段详情留在原文章，不在图里重复列全表。
  2. ChatRequestContext 隔离一个请求的工具预算、临时 Trace 和事件队列。Tool 写入，Service 读取；请求结束关闭。
  3. ConversationStorage 维护跨轮消息与 metadata。PG 是持久化来源，Redis 缓存消息和列表；metadata 中的 pending_hitl 不依赖请求 ctx 存活。
  4. runtime.py 持有共享模型，在每次请求中装配 Agent，并让知识工具绑定正确的 ctx。

重要实现取舍

save() 的真实实现是删除旧消息再重写完整历史，并非只追加一条新消息；会话 metadata 合并保存。load_with_meta() 即使消息缓存命中，也需要读取会话 metadata。原实现的 user_id 参数在存储层按 username 查用户，不能据参数名误画成整数用户主键。

与其他图的关系

[[图_7Agent对话编排模块]] 同时调用 Storage、ctx 和 Runtime；Runtime 装配 [[图_5工具层模块]]；Storage 下接 [[图_1数据存储模块]]。Pipeline 的 RAGState 定义仍在 [[图_4RAG工作流模块]]，不归本文件所有。

图形约定

绿色是目录，蓝色是文件，紫色是类，橙色是函数；标题中的名称与职责之间保留 12 个空格。类框中的编号通常对应其方法；函数框的编号描述内部步骤。没有组合，矩形宽高可分别调整。

知识工具

runtime.create_agent_for_request(ctx) 调用工厂得到与本次请求绑定的知识工具。工具内部先领取一次执行名额，再调用 [[图_4RAG工作流模块]]，把 Trace 和恢复快照存入 ctx；文本返回值交给模型，结构化状态由 Service 从 ctx 读取。

天气工具

get_current_weather_tool() 是装饰后的工具；get_current_weather() 是普通 HTTP 函数。tools/__init__.py 导出时将工具包装器重命名为 get_current_weather，因此 runtime 导入的名称与 weather.py 内普通函数同名，但指向装饰后的工具。

两个工具由模型选择；天气分支不经过 RAG，知识分支也不直接生成最终回答。

图_4RAG工作流模块

对应 [[4_代码实现_RAG Pipeline]]。根据问题复杂度和证据质量，决定返回证据、改写一次、请求澄清或报告无知识。

正常入口与两条执行路径

run_rag_graph() 初始化状态并执行 build_rag_graph() 编译出的图：

  1. 简单问题：首次检索 → Grader → 返回证据 / 改写一次再检索再评分 / HITL / 无知识。
  2. 复杂问题：复杂度规划时一并得到子问题 → Send 并行分发 → 每题固定“检索 → 评分” → synthesis() 合并证据与 Trace。子问题不会单独生成回答，也不走改写循环。

HITL 的实际实现

图执行结束时只生成最小恢复快照。[[图_7Agent对话编排模块]] 把快照放进会话 metadata 的 pending_hitl；下一轮经 resume_rag_from_hitl() 拼接补充、重新检索并评分，跳过外层 Agent 和原始复杂度分解。这里没有 Checkpointer / interrupt 暂停一个仍在内存里的图。

模块边界

RAGState 属于单次图执行；ChatRequestContext 属于单次请求；PendingHitlState 才负责跨轮等待。Pipeline 输出真实 Evidence 和路由状态，不承担最终答案生成。

图形约定

绿色是目录，蓝色是文件，紫色是类，橙色是函数；标题中的名称与职责之间保留 12 个空格。类框中的编号通常对应其方法；函数框的编号描述内部步骤。没有组合，矩形宽高可分别调整。

图_3检索模块

对应 [[3_代码实现_检索模块]]。输入查询，输出经过合并、重排和阈值过滤的证据及检索元数据。

主链如何衔接

retrieve_documents() → 候选数 → 共享模型编码 Query → Milvus L3 混合召回 → _finalize_retrieval() → Auto-Merging → Rerank Top-K → 分数过滤 → {docs, meta}。

Auto-Merging 只沿 parent_chunk_id 逐层查父块，不以 root_chunk_id 直接跳到 L1。父块缓存及数据库回查复用 [[图_1数据存储模块]]；查询向量复用 [[图_2文档入库模块]] 的 EmbeddingService。

需要区分的边界

  • 当前函数负责找证据，不负责判断证据是否足以回答；后者由 [[图_4RAG工作流模块]] 的 Grader 完成。
  • 改写预算由 Pipeline 控制。rewrite_query_once() 只执行一次改写调用，不自己决定是否重试。
  • Rerank 未启用或失败时仍返回检索排序结果；成功选出 Top-K 后再过滤，最终证据数量可能少于 K。

验证示例见本篇 §3 标注的 test/3_test_retrieval.py（教程中的示例路径，不是仓库现有 tests 目录）。

图形约定

绿色是目录，蓝色是文件，紫色是类，橙色是函数；标题中的名称与职责之间保留 12 个空格。类框中的编号通常对应其方法；函数框的编号描述内部步骤。没有组合，矩形宽高可分别调整。
