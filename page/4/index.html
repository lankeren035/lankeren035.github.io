图_2文档入库模块

对应 [[2_代码实现_文档入库]]。将原文解析成三级 Chunk；父块与叶块分别进入不同存储。

主要流程

  1. 调用 DocumentLoader.load_document()。PDF / Word / Excel 用现有加载器；HTML 先经过正文整理，然后回到统一入口。
  2. 每页先清洗再递归切出三层。父子 ID 随每一个 Chunk 一起生成，供后续 Auto-Merging 回查父块。
  3. 由调用方分离 L1/L2 和 L3：先调用 ParentChunkStore.upsert_documents()，再调用 MilvusWriter.write_documents()。本章测试中的 test_full_indexing_pipeline 展示了这一编排；不要额外理解成源码里已有一个入库 Pipeline 类。
  4. Writer 使用共享的 EmbeddingService 计算 Dense 向量，交给 MilvusStore 插入。BM25 由 Milvus 集合内的 Function 计算。

阅读重点

重点是 DocumentLoader 的统一返回结构、三级父子关系和 Writer 的输入边界。HTML 细节只在网页分支执行，不是所有文档都先转 HTML。图中没有纳入第 8 篇之后的上传接口和任务调度。

图形约定

绿色是目录，蓝色是文件，紫色是类，橙色是函数；标题中的名称与职责之间保留 12 个空格。类框中的编号通常对应其方法；函数框的编号描述内部步骤。没有组合，矩形宽高可分别调整。

图_1数据存储模块 · 详细实现

对应 [[1_项目设计]]。保留全部文件、类与逐函数分步内容。

读图方式

  1. 蓝底是文件，紫底是类，灰底是函数；框宽按文字自适应，标题与分步文本分开。
  2. 每个函数 / 类有唯一编号，例如 F01 / C01；步骤末尾 〔→ F07〕 表示调用或依赖对应编号。P 编号表示文件；P02:3 精确定位到 P02 文件的第 3 步，F04:2 定位函数 F04 的第 2 步。
  3. 只有相邻、能在文件内短距离连接且不穿越文字 / 其他函数框的关系画曲线。其余保留编号引用。重复使用的公共助手不再扇出多条长线。
  4. 编号仅用于查找，不表示全局执行顺序；每个框里的 1、2、3 才是该框的执行步骤。总图另有问答与入库主链。

图_1数据存储模块

对应 [[1_项目设计#3.1 数据存储模块|《1_项目设计》3.1 数据存储模块]] 的实现代码；风格参考 3DGS 笔记的“目录 → 文件 → 类 / 函数 → 编号功能说明”。

如何读图

  • 每个框的标题采用“名称 + 12 个空格 + 一句话职责”；框内保留编号功能说明。

  • 最外层是 backend；内部按真实目录分为 infra、db、indexing，根目录另放 env.py。

  • database.py 和 env.py 保留文件粒度；cache.py、models.py 及两个索引存取文件按必要的类或功能块展开。

  • 每条编号说明一个关键接口或职责；编号属于当前小框，不是整个系统的执行顺序。

  • 只画一条跨文件依赖箭头 Base；ParentChunkStore 的三个依赖直接写在文件框内，避免交叉连线。

主要关系

  1. 环境准备：load_env() → 导入存储模块；配置在模块初始化时读取。
  2. 关系库建表：models 中四个类继承 Base；init_db() 导入模型，再调用 metadata.create_all()。
  3. 父块存取：ParentChunkStore 调用 SessionLocal、ParentChunk 和 cache，组合 PG 持久化与 Redis 缓存。
  4. Milvus 访问：MilvusStore 经 milvus_client_session() 完成短连接操作；get_milvus_store() 复用的是 Store 实例。

对应文件

  • backend/env.py：环境变量加载。
  • backend/infra/database.py：引擎、会话工厂、ORM 基类、建表与 SQL 参数净化。
  • backend/infra/cache.py：RedisCache 和共享 cache 实例。
  • backend/db/models.py：User、ChatSession、ChatMessage、ParentChunk。
  • backend/indexing/milvus_client.py：Milvus 配置、连接和集合读写 / 检索。
  • backend/indexing/parent_chunk_store.py：父块 PG / Redis 存取。

范围

本图只覆盖本篇实现部分，不加入后续章节的文档解析、Embedding、Agent、接口鉴权或上传任务。字段与 ER 关系仍见 [[图_7数据库ER关系|图7]]；存储设计仍见 [[图_6数据存储与状态|图6]]。

文档中的验证入口为 test/1_test_storage.py，分别验证 PostgreSQL、Redis、Milvus 与 ParentChunkStore；测试代码位于 backend 目录之外，因此不放入目录框。
