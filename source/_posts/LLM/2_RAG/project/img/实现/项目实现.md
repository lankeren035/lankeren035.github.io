# 项目实现

基于 SuperMew-0.1.0 与博客第 1～7 篇的实现部分，将七张原生子图按主调用关系拼接。全部是可编辑矩形、文字和箭头，子图没有缩小字号。右侧保留整片空白扩展区，后续接入第 8 篇之后的模块。

## 总图怎么读

- 上排从左到右：对话编排 → 状态 / Runtime → 工具。
- 右侧从上到下：工具 → RAG 工作流 → 检索。
- 检索向左回到数据存储；左下文档入库也进入同一存储模块。
- 箭头连接模块边界，箭头旁点名实际调用入口。它表示列出的接口发生调用，不表示框内所有函数都调用对方。模块内部的文件、类和函数仍按子图原样展开。
- 蓝色实线是问答相关调用，蓝色虚线表示返回文本或状态，绿色是文档入库，紫色是 HITL 直接恢复，灰色是会话持久化依赖。没有接点的线交叉不表示合流。

## 两条业务流

### 用户问答

1. `chat_with_agent()` / `chat_with_agent_stream()` 从 ConversationStorage 加载历史与 metadata，建立本轮 ctx。
2. Runtime 通过 `create_agent_for_request(ctx)` 装配模型、提示词和工具。Service 构造长期笔记 + 最近 6 条历史 + 当前问题，调用 Agent。
3. 需要知识时调用闭包工具 → `run_rag_graph()`。Pipeline 做复杂度判断、证据评估和至多一次查询改写；复杂问题并行检索后合成 Evidence。
4. 所有检索入口复用 `utils.retrieve_documents()`，由 Milvus 召回 L3，再根据 parent_chunk_id 经 Redis / PG 获取父块，重排和过滤。
5. Pipeline 返回证据及 Trace；工具给模型带来源的片段，同时把 Trace / 快照写到 ctx。Agent 组织回答，Service 取走 Trace，并保存 AI 消息和 metadata。
6. 若要求用户澄清，Service 保存 pending_hitl。下一轮只有具备有效恢复快照时，才直接进入 `resume_rag_from_hitl()`，绕过外层 Agent 和复杂度规划；无快照走兼容回退。恢复后再回答或继续追问。

天气是独立 Tool 分支，不走 Milvus。流式分支通过 ctx 的 Queue 合并 rag_step 与文本；[DONE] 发出后仍执行笔记更新和落库。

### 文档入库

1. DocumentLoader 解析支持的格式；HTML 单独清理结构，然后仍回到统一逐页三级分块。
2. 调用方拆出 L1/L2 与 L3。L1/L2 先写 ParentChunkStore（PG + Redis）；L3 交给 MilvusWriter。
3. Writer 复用 EmbeddingService 编码 Dense 向量，再由 MilvusStore 写入全文、向量及关联 ID；BM25 在 Milvus 集合内计算。

这里的“调用方”对应第 2 篇完整入库测试所展示的编排，不额外虚构 IndexingPipeline 类，也不提前画第 8 篇之后的上传 / 任务接口。检索侧编码 Query 复用同一个 EmbeddingService；这项复用在检索子图中说明，总图不为每一条 import 再加横贯画布的线。
