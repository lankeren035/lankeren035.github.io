# 图_4RAG工作流模块

对应 [[4_代码实现_RAG Pipeline]]。根据问题复杂度和证据质量，决定返回证据、改写一次、请求澄清或报告无知识。

### 正常入口与两条执行路径

`run_rag_graph()` 初始化状态并执行 `build_rag_graph()` 编译出的图：

1. **简单问题**：首次检索 → Grader → 返回证据 / 改写一次再检索再评分 / HITL / 无知识。
2. **复杂问题**：复杂度规划时一并得到子问题 → `Send` 并行分发 → 每题固定“检索 → 评分” → `synthesis()` 合并证据与 Trace。子问题不会单独生成回答，也不走改写循环。

### HITL 的实际实现

图执行结束时只生成最小恢复快照。[[图_7Agent对话编排模块]] 把快照放进会话 metadata 的 pending_hitl；下一轮经 `resume_rag_from_hitl()` 拼接补充、重新检索并评分，跳过外层 Agent 和原始复杂度分解。这里没有 Checkpointer / interrupt 暂停一个仍在内存里的图。

### 模块边界

`RAGState` 属于单次图执行；`ChatRequestContext` 属于单次请求；`PendingHitlState` 才负责跨轮等待。Pipeline 输出真实 Evidence 和路由状态，不承担最终答案生成。


### 图形约定

绿色是目录，蓝色是文件，紫色是类，橙色是函数；标题中的名称与职责之间保留 12 个空格。类框中的编号通常对应其方法；函数框的编号描述内部步骤。没有组合，矩形宽高可分别调整。
